## Avant de déployer

Utilisez cette checklist avant de déployer sur le mainnet. Chacun de ces points a déjà piégé quelqu'un.

---

## Sécurité des smart contracts

### Contrôle d'accès

- [ ] `rule()` ne peut être appelée que par l'arbitre
  ```solidity
  require(msg.sender == address(arbitrator), "Only arbitrator");
  ```
- [ ] La création de litiges est réservée aux parties valides
- [ ] La soumission de preuves est restreinte de manière appropriée
- [ ] Les fonctions d'administration sont protégées (le cas échéant)

### Gestion de l'état

- [ ] Un litige ne peut pas être tranché deux fois
  ```solidity
  require(status == Status.Disputed, "Invalid state");
  status = Status.Resolved; // Update BEFORE external calls
  ```
- [ ] Les valeurs de décision invalides sont rejetées
  ```solidity
  require(_ruling <= numberOfChoices, "Invalid ruling");
  ```
- [ ] La décision `0` (refus d'arbitrer) est gérée explicitement
- [ ] Toutes les transitions d'état sont valides (aucun état n'est sauté)

### Protection contre la réentrance

- [ ] L'état est mis à jour avant les appels externes dans `rule()`
- [ ] Utilisez le pattern checks-effects-interactions
- [ ] Envisagez `ReentrancyGuard` pour une logique complexe
  ```solidity
  // BAD: external call before state update
  payable(winner).transfer(amount);
  status = Status.Resolved;
  
  // GOOD: state update before external call  
  status = Status.Resolved;
  payable(winner).transfer(amount);
  ```

### Sécurité des fonds

- [ ] Aucun fonds ne peut être bloqué définitivement
- [ ] Les transferts échoués ne bloquent pas le contrat
- [ ] Envisagez le modèle pull plutôt que push pour les retraits
- [ ] Testez avec des contrats comme destinataires (pas seulement des EOA)

## Configuration de l'arbitrage

### Choix de la cour

| Vérification | Statut |
|-------|--------|
| L'ID de la cour existe sur le réseau cible | ▢ |
| La cour traite votre type de litige | ▢ |
| Le stake minimum est acceptable | ▢ |
| Le calendrier de la cour convient à votre cas d'usage | ▢ |

**ID des cours Kleros V2 (Arbitrum One) :**

| ID de cour | Nom | Usage typique |
|----------|------|-------------|
| 1 | General Court | Par défaut pour la plupart des litiges. Bon point de départ. |
| 2 | Blockchain | Litiges techniques liés à la blockchain/aux smart contracts |
| 3 | Non-Technical | Litiges commerciaux, marketing et de contenu |
| 4 | Token Listing | Décisions de curation et de listing de tokens |
| 5+ | Spécialisées | Consultez [court.kleros.io](https://court.kleros.io) pour l'arborescence actuelle |

<Warning>
Les ID de cours sur Arbitrum Sepolia (testnet) diffèrent de ceux d'Arbitrum One (mainnet). Vérifiez toujours les ID à partir des [déploiements kleros-v2](https://github.com/kleros/kleros-v2/tree/dev/contracts/deployments) pour votre réseau cible.
</Warning>

Les paramètres des cours (minStake, feeForJuror, durées des sessions) sont soumis à la gouvernance et peuvent changer via des propositions de gouvernance. Interrogez-les via le getter `courts(courtID)` de KlerosCore plutôt que de les coder en dur.

### Extra Data

- [ ] `extraData` encode correctement l'ID de la cour et le nombre de jurés
  ```solidity
  bytes memory extraData = abi.encodePacked(
      uint96(1),   // courtID
      uint256(3)   // minJurors
  );
  ```
- [ ] Le nombre de jurés est impair (évite les égalités)
- [ ] Le nombre de jurés est adapté à la valeur du litige

### Gestion des frais

- [ ] Récupérez toujours un `arbitrationCost()` à jour avant de créer un litige
- [ ] Gérez les hausses de frais entre la vérification et l'exécution
- [ ] Remboursez l'excédent de frais à l'expéditeur
- [ ] Documentez qui paie les frais d'arbitrage

**Détails des frais spécifiques à Kleros :**

- [ ] En cas de paiement en ERC20 : vérifiez que le token figure dans `acceptedFeeTokens` sur KlerosCore
- [ ] En cas de paiement en ERC20 : appelez `arbitrationCost(extraData, feeToken)` (et non la surcharge ETH)
- [ ] En cas de paiement en ERC20 : autorisez (approve) KlerosCore à dépenser le montant des frais avant `createDispute()`
- [ ] Tenez compte des coûts d'appel : chaque tour d'appel double environ le nombre de jurés et le coût
- [ ] Pour les litiges cross-chain : la Foreign Gateway reflète `arbitrationCost()` localement, mais la synchronisation peut être en retard après des changements de gouvernance ; ajoutez une marge ou un mécanisme de nouvelle tentative

## Modèle de litige

### Qualité du contenu

- [ ] La question est claire et sans ambiguïté
- [ ] Toutes les options de décision sont mutuellement exclusives
- [ ] Les descriptions des décisions expliquent leurs conséquences
- [ ] Aucune option ne peut être interprétée de plusieurs façons
- [ ] Le scénario « Refus d'arbitrer » est documenté

### Aspects techniques

- [ ] Le JSON du modèle est valide
- [ ] Le modèle est stocké sur un stockage permanent (IPFS épinglé / Arweave)
- [ ] L'URI du modèle est accessible et se résout correctement
- [ ] `policyURI` pointe vers un document de politique valide
- [ ] `arbitratorAddress` correspond au déploiement
- [ ] `arbitratorChainID` correspond au déploiement

### Exemple de validation de modèle

```json
{
  "title": "Clear, specific title",           // ✓ Not generic
  "description": "Full context...",           // ✓ Sufficient detail
  "question": "Single, answerable question?", // ✓ Yes/no or clear options
  "answers": [
    {"id": "0x1", "title": "Option A", "description": "What happens if chosen"},
    {"id": "0x2", "title": "Option B", "description": "What happens if chosen"}
  ],
  "policyURI": "/ipfs/Qm...",                // ✓ Accessible
  "arbitratorChainID": "42161",              // ✓ Correct chain
  "arbitratorAddress": "0x991d2df165670b9cac3B022f4B68D65b664222ea"  // ✓ KlerosCore on Arbitrum One
}
```

### Document de politique

Chaque litige doit faire référence à un document de politique que les jurés utilisent pour prendre leurs décisions. Il est distinct du modèle : le modèle définit l'interface, la politique définit les règles.

- [ ] Le document de politique énonce clairement les critères de chaque option de décision
- [ ] La politique couvre les cas limites (exécution partielle, preuves ambiguës)
- [ ] La politique indique ce qui se passe en cas de « Refus d'arbitrer » (décision 0)
- [ ] La politique est rédigée pour un public non technique (les jurés sont issus du grand public)
- [ ] La politique est hébergée sur IPFS épinglé ou Arweave (pas sur une URL susceptible de changer)
- [ ] La politique a été relue, pour détecter les ambiguïtés, par quelqu'un qui ne connaît pas votre protocole

<Tip>
Étudiez les politiques Kleros existantes des produits en production. Les politiques d'Escrow V2 et de Curate V2 sont de bons modèles. Vous pouvez les trouver sur IPFS via le champ `policyURI` du modèle de litige ; inspectez les litiges en cours sur [court.kleros.io](https://court.kleros.io) pour voir des exemples.
</Tip>

### Calendrier du cycle de vie d'un litige

Les litiges Kleros suivent une séquence de phases fixe. Comprenez l'impact de ce calendrier sur votre application :

| Phase | Durée (General Court) | Remarques |
|-------|--------------------------|-------|
| Preuves | ~3 jours | Chaque partie peut soumettre des preuves |
| Vote | ~3 jours | Les jurés émettent des votes chiffrés (Shutter) |
| Appel | ~5 jours | La partie perdante peut financer un appel |
| **Total (sans appel)** | **~11 jours** | Délai minimum avant décision |
| **Par tour d'appel** | **+~11 jours** | Chaque tour ajoute à peu près la même durée |

- [ ] Votre application tolère le délai de résolution des litiges (1 à 4 semaines en général)
- [ ] Les fonds ou l'état restent bloqués pendant le litige sans causer de problèmes
- [ ] Les utilisateurs sont informés des délais attendus dans votre interface
- [ ] Vous gérez le cas où les appels allongent considérablement le délai

## Préparation opérationnelle

### Surveillance

- [ ] Alerte sur les événements `DisputeRequest`
- [ ] Alerte sur les événements `Ruling`
- [ ] Surveillance des changements de frais d'arbitrage
- [ ] Suivi des délais de résolution des litiges
- [ ] Tableau de bord des litiges actifs

**Surveillance spécifique à Kleros :**

- [ ] Surveillez les événements `AppealDecision` de KlerosCore : les appels modifient le calendrier et le coût
- [ ] Abonnez-vous aux changements de paramètres des cours via les événements `CourtModified` : les changements de frais affectent vos calculs de coûts
- [ ] Suivez vos litiges sur [court.kleros.io](https://court.kleros.io) en filtrant par l'adresse de votre contrat
- [ ] En cas de cross-chain : surveillez l'état des claims/challenges du bridge Vea sur [veascan.io](https://veascan.io)
- [ ] Mettez en place des alertes pour l'événement `Paused` de KlerosCore : un arbitre en pause bloque les nouveaux litiges et les décisions

### Documentation

- [ ] Guide utilisateur pour la création de litiges
- [ ] Instructions pour la soumission de preuves
- [ ] Explication des issues possibles des décisions
- [ ] FAQ pour les questions courantes
- [ ] Contact de support en cas de problème

### Réponse aux incidents

- [ ] Plan pour le scénario d'un arbitre en pause
- [ ] Plan pour une décision inattendue
- [ ] Contact d'urgence chez Kleros (si nécessaire)
- [ ] Procédure de mise à niveau documentée (si le contrat est upgradeable)

**Scénarios de défaillance spécifiques à Kleros :**

- [ ] **Arbitre en pause :** KlerosCore dispose d'un mécanisme de pause d'urgence contrôlé par le rôle Guardian. En cas de pause, aucun nouveau litige ne peut être créé et aucune décision ne peut être rendue. Votre contrat doit gérer proprement un revert de `createDispute()` et informer les utilisateurs.
- [ ] **Décision 0 (Refus d'arbitrer) :** Cette décision signifie que les jurés ont jugé le litige invalide. Votre contrat doit gérer ce cas explicitement : ne le traitez pas comme la victoire de l'une des parties.
- [ ] **Égalité des votes :** Dans le DisputeKitClassic actuel, une égalité des votes aboutit par défaut à la décision 0 (refus d'arbitrer), sauf si elle est renversée en appel. Concevez votre gestionnaire de la décision 0 pour produire une solution de repli raisonnable (par ex. rembourser les deux parties).
- [ ] **Changement d'adresse du contrat :** Les contrats V2 sont des proxies upgradeables. Après des audits de sécurité, les adresses peuvent être conservées mais l'implémentation peut changer. Si vous stockez l'adresse de l'arbitre en `immutable`, vous ne pourrez pas vous adapter : envisagez d'utiliser une adresse modifiable par un governor.
- [ ] **Délai du bridge Vea (cross-chain uniquement) :** Dans le scénario défavorable, la transmission de la décision peut prendre ~7 jours via le bridge natif d'Arbitrum. Assurez-vous que votre état bloqué peut perdurer au moins 2 semaines sans causer de problèmes aux utilisateurs.

## Kleros V2 sur le mainnet

Kleros V2 (Neo) est en production sur le mainnet **Arbitrum One**. L'accès à la cour est ouvert à tous : les utilisateurs peuvent staker du PNK et participer en tant que jurés. Ces points restent pertinents pour les intégrateurs :

- [ ] **Mises à niveau des contrats :** Les contrats V2 utilisent des patterns de proxy UUPS et peuvent être mis à niveau via la gouvernance. Abonnez-vous au [blog Kleros](https://blog.kleros.io) et au [Discord](https://discord.gg/MhXQGCyHd9) pour recevoir les annonces.
- [ ] **Stabilité du subgraph :** Épinglez une version spécifique de déploiement du subgraph en production. Consultez le [README du subgraph kleros-v2](https://github.com/kleros/kleros-v2/tree/dev/subgraph) pour les derniers ID de déploiement stables.
- [ ] **Statut du SDK :** `@kleros/kleros-sdk` est en développement actif. Pour une stabilité maximale, vous pouvez interagir directement avec les contrats via les ABI de `@kleros/kleros-v2-contracts`.

- [ ] **Testnet d'abord :** Déployez et testez toujours un cycle de vie complet de litige sur Arbitrum Sepolia avant le mainnet. Les litiges sur testnet peuvent prendre plus de temps à être résolus en raison d'une participation limitée des jurés.

<Note>
Contactez l'équipe Kleros via [Discord](https://discord.gg/MhXQGCyHd9) ou `integrations@kleros.io` avant votre premier déploiement en production. L'équipe peut relire votre modèle de litige et vous conseiller sur le choix de la cour.
</Note>

    uint96 parent,

## Problèmes fréquents de dernière minute

<AccordionGroup>
  <Accordion title="Mauvaises adresses réseau">
    Vérifiez bien que vous n'utilisez pas des adresses de testnet sur le mainnet, ou inversement. KlerosCore sur Arbitrum Sepolia a une adresse différente de celle sur Arbitrum One.
  </Accordion>

  <Accordion title="Modèle non épinglé">
    Le contenu IPFS disparaît s'il n'est pas épinglé. Utilisez Pinata, Infura ou Arweave pour garantir sa permanence. Kleros héberge un service d'épinglage sur `cdn.kleros.link`, mais vous devriez également épingler de votre côté.
  </Accordion>

  <Accordion title="Frais codés en dur">
    Ne codez jamais en dur les frais d'arbitrage. Récupérez-les toujours dynamiquement. Les frais changent via la gouvernance et varient selon la cour.
  </Accordion>

  <Accordion title="Logique de remboursement manquante">
    Si l'utilisateur paie trop de frais d'arbitrage, remboursez l'excédent.
  </Accordion>

  <Accordion title="Mauvais encodage des extraData">
    V2 utilise `abi.encodePacked(uint96(courtID), uint256(jurorCount))` : notez le `uint96` pour l'ID de la cour, et non `uint256` comme dans V1. Utiliser `uint256` encodera une cour différente de celle prévue.
  </Accordion>

  <Accordion title="Nombre de jurés pair ou impair">
    Utilisez toujours un nombre impair de jurés (3, 5, 7) pour éviter les égalités de votes. Dans DisputeKitClassic, une égalité aboutit par défaut à la décision 0 (refus d'arbitrer), ce qui n'est peut-être pas ce qu'attendent vos utilisateurs.
  </Accordion>

  <Accordion title="Modèle de litige non enregistré">
    Si vous utilisez `templateId`, assurez-vous que `setDisputeTemplate()` a été appelée sur le `DisputeTemplateRegistry` et que vous avez stocké le `templateId` renvoyé. Si l'ID est incorrect, l'interface de la Court n'affichera pas correctement votre litige et les jurés manqueront de contexte.
  </Accordion>
  </AccordionGroup>
